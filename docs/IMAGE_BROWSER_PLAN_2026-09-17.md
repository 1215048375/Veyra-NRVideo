# 图片浏览器与预解码顺序修复

用户要求：检查等待后下一张仍慢的问题；增加原图缩略图列表，选中后才增强单张，不预处理相邻图片；可上一张/下一张，返回列表，并支持双击图片返回。

## 实现

- `ImageFolder::prefetchWindow` 与浏览列表共用文件顺序，当前与后续优先，剩余额度才用于前面的图片。保持最多20张、512MiB CPU缓存。
- `ImageDecodeCache` 在窗口变化后保留仍被需要且文件身份未变的在途结果，避免丢弃后重复解码。已离开窗口的结果仍丢弃。
- `ImageBrowser` 是独立 Win32 子窗口；单个后台 WIC 线程生成最长边160像素的原图缩略图，按可见行及一行缓冲排队，最多缓存512张缩略图。保留JPEG方向信息。浏览列表不启动EngineController处理图。
- 目录默认进入原图列表；点击后复用原图片处理入口，只处理选中图片；上一张/下一张仍按相同目录顺序。返回停止当前处理，保留列表缓存、选中位置和可见滚动位置。传统预解码模式保留在图片菜单独立入口。
- 图片区域双击和左栏返回按钮共用返回动作。列表只接受从自身按下开始的点击，避免双击返回后的鼠标松开事件误打开另一个缩略图。

## 证据与边界

2026-09-17完成构建、队列回归和真实应用 HWND 操作测试，详见 WORKLOG 同日条目与 out/ci-dependencies/image-browser-* 日志。没有改动运行组件、SDK或FFmpeg，也没有发布。

原20张功能是CPU预解码，不是20张NR增强结果预渲染。尺寸不一致、缓存预算不足、未命中以及增强本身仍可能带来延迟；本次不宣称消除了大图NR渲染耗时。新浏览器使用按需处理避免不必要的增强排队。实测为基础PNG图片且NR/SR/FG关闭，增强Create/Evaluate及大图实际性能未执行。下一步：用户实际目录、缩略图显示及开启增强后的体验验收。

## 用户复测后修复（同日）

## 继续修复：不同尺寸保留设备

用户继续授权后，普通图片缓存命中、配置一致时，异尺寸切图也交给同一GPU线程。排空一次队列，释放旧输出lease，保留D3D12设备与命令队列，仅重建尺寸相关graph/presenter与AVFrame；按真实原图尺寸重算ResolutionPlan，不靠缩放/填充原图伪造命中。SourceSwitch源序号/epoch连续递增，记录实际drain/destroy/create时间。分块大图输入/输出两侧均排除，不向不会消费pendingImage的分块循环投递请求。

RTX3080本机基础图320×180→128×96→320×180，保存红/绿/蓝像素和尺寸验证通过，设备初始化仅一次；最终异尺寸切换CPU观测71.69/85.04ms，同尺寸1.59ms。旧路径重建设备本身约0.5秒。测量不是屏幕延迟或NR性能承诺，增强关闭，NR/SR/FG Create/Evaluate未执行。最终干净目录out/packages/Veyra-1.2.0-local-20260917-image-fix2，详见WORKLOG。

## 后续：缩略图色彩与保留设备选项

用户反馈缩略图仍偏亮，要求可一直保留图片GPU设备。新增图片菜单选项，默认关闭；UiPreferenceStore v4保存，兼容v1–v3默认关闭。EngineController工作线程持有一套设备/命令队列，COM生命周期覆盖整个工作线程；开启后跨图片会话/返回列表/缓存未命中继续复用。同一套ring保持fence单调，不另建从1开始的fence队列。释放图片纹理和处理图；禁用后空闲时释放，非图片来源、device removed和退出释放。只保留device/queue，不承诺保留NR模型/增强结果；设备故障HRESULT记录并恢复重建。

缩略图原来缺少内嵌ICC/EXIF色彩处理，现按[WIC ColorTransform](https://learn.microsoft.com/en-us/windows/win32/api/wincodec/nf-wincodec-iwiccolortransform-initialize)转sRGB一次，未标记图沿用原像素解释，不统一压暗。灰阶128保持128，高光245得到246/245/245，gamma3配置的128转换为99；对应LittleCMS参考100，差异≤1。此证明色彩路径正确处理这些样本，不代表已复现用户原图或HDR桌面的全部视觉差异。

完整构建、620图/两种DPI回归、v4保存/v3迁移、真实三次图片会话仅一次device创建及禁用释放通过。最终本地目录为out/packages/Veyra-1.2.0-local-20260917-image-fix3。NR/SR/FG关闭，增强运行与实际device-lost注入未执行。下一步用户用原图复测缩略图及选项。

## 白色蒙层复报：玻璃背景的 alpha 合成修复

用户截图仍呈现整体发白。检查发现主窗口启用全客户区 DWM glass，而图片浏览器的 GDI 填充、文字与 StretchDIBits 输出没有恢复 alpha，产生 RGB 非零、alpha 为零的画布。它不满足透明合成的预乘约定。此前 ICC 测试只验证 GetPixel 的 RGB，不能覆盖这个缺陷，也不能证明用户的发白已经修好。

PaintBuffer 增加显式 makeOpaque，仅由 ImageBrowser 在全部绘制完成后调用；刷新 GDI 写入后将画布 alpha 设为255，保持 RGB 不变，其他玻璃控件不受影响。新增实际 WM_PRINTCLIENT 画布逐像素 alpha 检查，修改前失败，修改后620图/两种DPI滚动与返回顶部通过；ICC/RGB测试仍保持原值。构建与独立包基础播放通过，证据见 WORKLOG。新目录 out/packages/Veyra-1.2.0-local-20260917-image-fix4。用户截图对应原文件和桌面最终合成效果尚待用户目视复测；本次不是降低曝光。
